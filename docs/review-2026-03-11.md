## 5. Fly.io Deployment Timing

### Current deployment state

- **Docker setup exists**: `docker/Dockerfile.api`, `docker/Dockerfile.web`, `docker/compose.yaml`,
  `docker/start.sh`
- **Dockerfiles use Bun 1.3.5** (matches `packageManager` in root package.json)
- **compose.yaml** targets Docker Compose with Portainer (ghcr.io images, external networks)
- **No Fly.io config exists** (no `fly.toml`)
- **MVP.md says**: "Docker, docker-compose (Portainer-ready)" for deployment

### Fly.io: Now or after Feature 04?

**Recommendation: Deploy NOW (before Feature 04)**

Reasons:

1. **MVP "Done" criteria #1 is "Deployed to a public URL"** — it's been deferred long enough. Having
   a live URL validates the Docker build, runtime config, and database setup before adding more
   features.

2. **Feature 04 (Check Logging) adds database complexity** — new tables, calculated fields
   (`nextDueAt`), and queries that benefit from testing in a real environment. Better to have
   deployment working BEFORE adding that complexity.

3. **Current state is deployable** — Auth, Vehicle CRUD, Check Types CRUD, and the design system are
   all complete. The app is usable and presentable.

4. **Catch deployment issues early** — Docker builds, environment variables, SQLite persistence on
   Fly.io volumes, CORS config, API↔Web networking — all of these can surface surprises. Better to
   discover them now with a simpler app.

5. **Fly.io supports both apps** — You'll need two Fly apps (api + web) or a combined approach. The
   existing Docker setup separates them cleanly.

### Fly.io considerations

- **SQLite on Fly.io** requires a persistent volume (Fly Volumes). The current Docker setup already
  uses a `/data` volume for the database.
- **Single region** recommended for SQLite (no distributed reads). Fine for a personal/family app.
- **Two services**: api (port 3000) + web (port 4321). Can use Fly's internal networking.
- **Environment variables**: `DATABASE_URL`, `API_URL`, `PUBLIC_API_URL`, auth secrets.
- **Existing Dockerfiles** may need minor tweaks for Fly.io (health checks, fly.toml config) but the
  multi-stage build approach is solid.
